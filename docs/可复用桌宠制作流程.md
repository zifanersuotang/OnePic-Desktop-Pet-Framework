# 可复用桌宠制作流程

## 1. 新建独立工作区

```powershell
.\scripts\check_environment.ps1
.\scripts\new_pet.ps1 `
  -PetId "new-pet" `
  -DisplayName "新桌宠" `
  -Source "图片或视频绝对路径" `
  -SelfieFrame "视频代表帧，可选" `
  -Mode full-body `
  -RecommendedDisplayHeight 220
```

`Mode` 支持 `full-body`、`half-body`、`animal`、`vehicle-seated` 和
`static`。载具、坐姿或静止项目可用替代互动，但同样必须提交预览并确认。
这类项目没有八相位走路时，构建器只在替代互动哈希审批有效的前提下生成静止
占位序列，并写入 `stationary=true`，不会进入普通自主走动。
其中 `full-body`、`animal` 只允许八相位走路；`half-body` 默认走路，只有显式提交
替代互动且没有批准走路时才可走后备路线。若两种证据都已批准，验证与发布最小
workflow 始终选择走路。
虚构角色或旧生成素材没有原始照片时，可把 `pet-config.json` 的
`selfie_required` 设为 `false`；动画用的 `actions/transparent/selfie.png`
仍是八种动作之一，但不属于私人原图。

每只宠物的配置、来源、候选、动作、走路、复核、运行版本、备份和审批都位于
`user_assets/pets/<pet-id>/`。审批只保存在该目录的 `workflow.json`，
全局 `active-pet.json` 只指向当前宠物。

### Agent 观察—行动闭环

新建工作区后、接手已有工作区时，以及每次变更、用户审批、命令失败或构建完成后，
都运行：

```powershell
.\.venv\Scripts\python.exe .\tools\pet_workspace.py agent-status new-pet
```

该命令只读地重算当前阶段、阻塞原因、证据哈希和唯一安全下一步。Agent 每轮只执行
一个 `allowed_next_actions`，随后重新观察；`must_pause=true` 时必须等待报告指定的
用户输入或视觉确认。它不能代替原分辨率角色检查、逐张动作质检、走路 GIF 或真实
窗口验收，也不会写第二份审批状态。展示当前证据后，只有用户对该证据明确通过或
否决，才执行相应字段。无占位符的 `command`、`approval_command`、
`rejection_command`、`recovery_command` 可原样执行；带 `{...}` 的
`command_template`、`rejection_command_template`、`recovery_command_template`
不可直接执行，只能收集 `required_inputs` 明列的路径、原始反馈或诊断依据，并安全
转义成单个参数后渲染。不得添加、猜测或复用旧输入；执行后立即重新观察。

### 生产路线选择

- 用户未明确提出 Live2D、Cubism 或混合版：保持默认
  `-RenderingMode sprite`，执行升级基础款，即 38 帧基础配方 + 新宠物默认
  两张摸头过渡帧；
- 用户明确提出“进阶版”“扩展动作”或点名某项能力时，才在升级基础款之后
 追加多帧扩展包。扩展包逐组制作、逐组预览、逐组确认，并与当前素材
  SHA-256 绑定；
- 推荐的进阶图像包是招牌动作、专注工作、跳跃、等待回应和六帧微表情。
  普通建宠请求不会自动携带这些动作；
- 纯本地互动台词和侧面走路进入进阶需求确认清单，但必须由用户明确选择：
  台词不联网、不读取输入内容；侧面走路保留正面八相位并作为第二种样式；
- 八向视线不属于进阶版默认内容，也不能由参考图、历史项目或“功能丰富”
  等描述推断启用。只有用户明确点名“八向视线/跟随鼠标视线”时才能制作，
  新工作区固定从 `directional_mouse_follow.enabled=false` 开始；
- 用户明确要求 Live2D/Cubism/混合版：初始化时传
  `-RenderingMode hybrid-live2d`。仍先完成同一套角色、动作、摸头和走路门禁，
  再追加 Live2D 待机层；
- Live2D 只增强 idle，不替代走路、坐睡、拖拽、自拍、表情或摸头状态。混合
  层失败时回退到基础款精灵；
- `rendering_mode=sprite` 与启用的 `hybrid_runtime` 同时出现时，构建必须失败，
  防止普通建宠请求被悄悄升级成实验路线。

### 基础与进阶共享的活动区域

所有 Windows 宠物自动继承右键“活动区域”，不需要修改 `pet-config.json`、
`workflow.json` 或运行 manifest，也不增加素材帧。框架默认：

- `movement_region_enabled=false`、`movement_region=null`；
- 首次启用时，以角色当前位置为中心生成不超过 `800×500` 的屏幕内矩形；
- 用户可输入全局坐标 `X, Y, 宽, 高`，开关和矩形随本机用户设置持久化；
- 自主走动和追鼠标使用该矩形；手动拖动、缩放和“回到主屏幕”不受矩形限制，
  但继续使用可见轮廓屏幕边界，防止角色彻底丢失；
- 切换开关和拖动松手不立即改写位置；自主行为再次开始时才应用区域边界。

分享版不得写入制作者的本机矩形或绝对屏幕坐标。该能力是运行偏好，不需要角色、
走路或扩展包审批，也不能计入 40/65/73 帧口径。

Windows 基础版和进阶版也默认保留双击精简聊天入口与晶体回复气泡。打开窗口本身
不得联网；它不等于启用纯本地随机台词或云聊，只有用户主动配置云端服务并发送时
才允许请求。sprite 与 hybrid 分享包都必须执行真实双击和零联网烟测。

## 2. 两次人工门禁

只生成一张标准形象，登记并让用户确认：

```powershell
.\.venv\Scripts\python.exe .\tools\onepic_workflow.py `
  --pet-id new-pet character-candidate `
  --image "user_assets/pets/new-pet/candidate/approved.png" `
  --style preserve_original
.\.venv\Scripts\python.exe .\tools\onepic_workflow.py `
  --pet-id new-pet approve-character
```

确认后先通过“单动作候选门”制作八种动作，再制作八相位走路并生成走路预览。

### 基础动作源帧门禁

1. 每次只描述和生成一个动作，不得把挥手、拿道具、起身等多个职责写在同一批次；
2. 每批只生成 2–3 个候选，保存到
   `actions/candidates/<action>/<batch-id>/`；
3. 所有候选只能以 `candidate/approved.png` 为身份锚点；如果出现四手、断肢或粘连，必须丢弃该批逻辑并回到标准角色，禁止用残次帧继续修改；
4. 逐张检查肢体完整、单一动作、身份一致、无道具粘连和轮廓干净；
5. 只有五项全部通过的候选才能执行：

```powershell
.\.venv\Scripts\python.exe .\tools\pet_workspace.py action-review new-pet `
  --action wave `
  --candidate "actions/candidates/wave/v1/candidate_01.png" `
  --candidate "actions/candidates/wave/v1/candidate_02.png" `
  --selected "actions/candidates/wave/v1/candidate_02.png" `
  --limb-integrity-ok --single-action-ok --identity-ok `
  --no-fused-props --clean-silhouette --yes
```

该命令才会把选中帧写入 `actions/transparent/<action>.png`，并生成
`review/action-source-gate.json`。缺少任一动作记录、五项检查不全、标准角色变化或入库 PNG 被替换，都会阻止构建。

八种动作全部通过后制作八相位走路。先重新观察并执行报告的预览命令；展示当前
走路 GIF 与八帧后，依据用户本轮决定原样执行
`decision.approval_command`，或将 `required_inputs.user_feedback` 安全填入
`decision.rejection_command_template`：

```powershell
.\.venv\Scripts\python.exe .\tools\pet_workspace.py agent-status new-pet
```

角色、走路或替代互动确认都与当前素材 SHA-256 绑定；文件变化会使旧确认失效。
`static` 与 `vehicle-seated` 没有八相位走路时，按报告的 `decision.command` 使用
`interaction-review --mode ... --preview ...` 提交当前互动预览；重新观察进入
`awaiting_interaction_approval` 后展示预览，再执行报告给出的批准或否决命令。否决
会保留原始反馈并进入修订阶段；命令同时 CAS 绑定预览哈希与 mode，新预览必须
重新提交，不能直接改成 approved。`full-body`、`animal` 不得使用该后备路线；已有
批准走路时，走路也优先于互动进入发布最小 workflow。

### 进阶动作的追加门禁

基础角色和走路通过后，只有用户明确选择进阶版或具体动作包才进入以下循环：

1. 每组动作写入独立版本目录，不覆盖上一版；
2. 生成透明 PNG 帧、GIF、联系表和素材哈希报告；
3. 用户直接确认该组动作后，将确认与当前帧束 SHA-256 绑定；
4. 运行素材、行为、配置、流程和窗口测试；
5. 全部通过后才激活；修改任一帧都会使该组旧确认失效。

标准建议帧数为：招牌动作 3–4 帧、专注工作 4–6 帧、跳跃 4–5 帧、
等待回应 3–4 帧、微表情 6 帧。常用进阶样例为 65 帧；再加侧面八相位为
73 帧，互动台词不增加图片。完整契约见 `docs/进阶版桌宠定制框架.md`。

### 微表情、台词与侧面走路

- 微表情推荐 `calm/skeptical/surprised/shy/pensive/happy` 六帧，保持同一构图和
  身体，只改变眼眉、嘴形和脸颊；按普通扩展包生成 GIF、联系表和帧束哈希；
- 互动台词按动作提供 3–6 句，先做实机气泡预览，再把规范化配置语义哈希和确认
  原文写入 `workflow.json.feature_status.local_dialogue_vN`；
- 侧面走路先只生成一张侧身模型供用户确认，再制作接触、下压、经过、抬升的
  双脚八相位；侧面帧束需单独 GIF、联系表和哈希确认；
- 侧面走路配置为 `walk_variant=true`、`walk_variant_default=false`，
  `replaces_forward_walk=false`；右键切换选择并按宠物保存；
- 以上三个模块互相独立，修改或撤下其中一个不能连带废止其他已批准模块。

八向视线使用独立开关和独立确认，不随上述四组动作自动加入。用户要求移除时，
只需把 `directional_mouse_follow` 恢复为 `{"enabled": false}` 并重新构建；
历史候选和审批记录保留，但运行清单与分享包不得再包含视线帧。

## 3. 声明式动画配方

`config/animation-recipe.v1.json` 定义固定顺序和复用关系：

- idle 6、walk 8、sit 5、sleep 5、drag 3、selfie 4；
- wave、happy、shy、surprised、annoyed、sleepy、curious 各 1；
- 合计 38 帧基础配方；
- 新宠物默认制作并要求 `touch_soften.png`、`touch_return.png` 两张摸头
  过渡图，因此默认总数为 40；
- 迁移的旧宠物可按已声明配方提供 0–2 张，总数因此兼容 38、39 或 40。

旧宠物没有摸头过渡图时，程序在内存中混合已验收的反应帧与 idle 帧，不要求补图。
但若迁移项目的配置要求专用过渡帧，而现有文件缺少
`review/touch-transitions.json` 来源取证，不能静默沿用：按 `agent-status` 的
`touch-transitions` 命令从当前已批准角色与动作确定性重建，原文件移入可恢复备份，
新帧及其 runtime 必须重新做视觉验收。

## 4. 摸头反馈

头部点击区来自当前缩放后的 alpha 轮廓顶部窄带。默认时序：

1. `surprised` 320 ms；
2. `shy` 或 `happy` 760 ms；
3. 每张专用过渡帧 180 ms；缺失时使用内存混合帧；
4. idle 混合停留 160 ms，然后恢复自动状态机。

默认分支为 `weighted_no_repeat`，权重 shy 0.55 / happy 0.45，且不连续重复。
也可在 `pet-config.json` 的 `touch_feedback` 里设置
`fixed_shy`、`fixed_happy`、`alternate` 或 `weighted`。默认节流 1400 ms，
播放期间再次点击会忽略；拖拽或双击可安全抢占，不会堆叠状态。

## 5. 装配、QA 与回滚

```powershell
.\.venv\Scripts\python.exe .\tools\pet_workspace.py validate new-pet
.\scripts\build_pet.ps1 -PetId new-pet -Activate
```

所有输出先进入 `staging/`。构建前先校验 `action-source-gate.json` 的候选数、五项视觉质检、标准角色哈希和正式动作哈希。自动 QA 再检查画布、透明角、边距、绿边、
alpha mass、走路形变/起伏/接缝和可选摸头帧。静态动作默认允许 12% 偏差，
坐睡过渡允许 22%；目标取已确认走路帧 alpha mass 中位数与所有静态动作安全上限
的共同最小值，低于走路中位数 60% 时停止。

失败 staging 移到 `failed-builds/`，现有 runtime 不变；这种失败只检查诊断，
不要运行回滚或重复同一构建命令。`agent-status` 会进入
`build_failure_recovery`；只有确认是可重试的瞬态失败后，才原样执行当前
无占位符 `decision.recovery_command`，或把具体诊断依据安全填入
`required_inputs.diagnostic_reason` 后渲染 `recovery_command_template`，归档诊断并
开放一次重试。成功后才原子激活，上一版本
保存在 `backups/`。若成功激活的新版本随后被用户否决，先核对
`user_assets/active-pet.json` 指向目标宠物，再回滚：

```powershell
.\scripts\rollback_pet.ps1
```

复核产物包括透明动作 PNG 合集、JPG/PNG 动作接触表、walk GIF、
sit-sleep-wake GIF、touch-feedback GIF、`assets-qa.json` 和历史 build
目录。runtime manifest、顶层 QA 与 `latest-build.json` 必须绑定同一 build ID
和当前配置、审批、正式素材的输入指纹；旧 `status=passed` 不能单独代表当前构建。

窗口 QA 还需验证活动区域默认关闭；开启后自主走动与追鼠标不越过矩形；角色可
手动拖出矩形且松手不跳回；关闭后恢复当前屏幕可用区域；重启后本机开关和坐标
保持；完全落在屏幕外的矩形安全回退到当前屏幕。

## 6. 一条命令发布

用户查看当前 build 的 GIF、联系表、QA 和真实窗口后重新观察。只有用户明确通过
当前证据，才原样执行 `decision.approval_command`；否决时执行无占位符
`decision.rejection_command`，或用 `required_inputs.user_feedback` 安全渲染
`decision.rejection_command_template` 并保留反馈。两种结果都必须再次运行：

```powershell
.\.venv\Scripts\python.exe .\tools\pet_workspace.py agent-status new-pet
```

通过后的观察必须返回 `ready_to_release`。仅修改配置中的 `sharing` 授权不会废止
runtime 验收；应用源码、打包资源、配方、运行配置或已批准素材变化会改变构建输入，
必须重新构建和验收。随后再发布：

```powershell
.\scripts\release_pet.ps1 -PetId new-pet -Mode share-no-selfie
```

模式：

- `private-local`：本机包，可含自拍；
- `share-with-approved-selfie`：只有配置中的明确自拍 SHA-256 许可匹配时才含自拍；
- `share-no-selfie`：分享包不含自拍。

准备阶段生成 schema v2 `package-preparation.json`：包含随机 `preparation_id`、
`prepared_at`、当前 QA SHA-256、包内活动指针 SHA-256、最小 workflow SHA-256 与
可选自拍 SHA-256。finalize 会重新读取当前 workflow/QA/runtime 验收；
`share-with-approved-selfie` 还会重查配置许可哈希与源自拍，包内自拍必须逐字节匹配
准备报告哈希，任何变化都要求重新 prepare。

finalize 必须读取 schema v1 且 `status=passed` 的六份 JSON：UnitOnly 测试、源码
启动、成品启动、互动菜单、源码双击聊天和成品双击聊天。除测试外五份报告必须匹配
当前 `build_id` 与 `runtime_manifest_sha256`；Hybrid 报告也必须绑定当前 pet/runtime，
防止复用同一 pet-id 的旧烟测。成品启动与成品双击两份证据还必须同时匹配最终
EXE SHA-256、完整 one-dir `distribution_sha256`、pet-id 和
本次 `preparation_id`；烟测后替换 `_internal` 任一文件都会失败，命令退出码或
passed 布尔值不能代替证据文件。

隐私扫描只对 `_internal/PySide6` 随附 vendor 源中的 `source` 目录名作窄豁免；
`_internal/user_assets` 下的 source、candidate、drafts、backups、failed-builds、
staging 一律拒绝。源码与成品烟测会隔离可能重定向设置、用户目录、宠物清单、
演示素材、陪伴数据或测试模式的环境变量，并在结束后恢复；新增恢复
`ONEPIC_TESTS_PASSED`、`ONEPIC_INCLUDE_USER_ASSETS`、`ONEPIC_PACKAGE_USER_ROOT`、
`ONEPIC_INCLUDE_SELFIE_ASSET`。之后依次完成源码烟测、EXE 构建、成品内真实双击
快捷聊天烟测、隐私扫描、
逐文件 CRC/SHA、ZIP CRC 和归档 SHA-256，并交付整个
`dist/OnePicDesktopPet` 的 ZIP 与 release report。原图、视频、参考、
草稿、候选和备份永不进入发布暂存区。

## 7. 历史项目迁移

旧全局审批按明确项目迁移：

```powershell
.\.venv\Scripts\python.exe .\tools\onepic_workflow.py `
  migrate-legacy <pet-id>
```

已有 38 帧项目只有在 candidate、八帧走路、passed QA、runtime manifest
和人工 walk GIF 全部存在时才可重建独立哈希门禁：

```powershell
.\.venv\Scripts\python.exe .\tools\pet_workspace.py `
  migrate-existing <pet-id>
```

如果迁移后的配置要求摸头过渡帧但缺少来源记录，必须按 `agent-status` 重建：工具会
先备份旧过渡帧，再从当前已批准素材确定性生成并写入新取证；不得把旧文件静默视为
可信，重建后的 build 需要重新展示和验收。

## 8. 显式 Live2D 追加流程

仅当用户明确选择混合路线时执行：
